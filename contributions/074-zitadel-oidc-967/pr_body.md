## Description

# Which Problems Are Solved

- `client.Discover()` did not check the `Content-Type` of the discovery response. OpenID Connect Discovery 1.0, [section 4.2](https://openid.net/specs/openid-connect-discovery-1_0.html#ProviderConfigurationResponse), requires the response to use `application/json`; any body that happened to decode as JSON (e.g. served as `text/plain` or `text/html`) was accepted.

# How the Problems Are Solved

- Adds `httphelper.HttpJSONRequest`, which behaves exactly like `HttpRequest` but, for a `200 OK` response, requires the media type to be `application/json` (parsed with `mime.ParseMediaType`, so parameters such as `charset` and case differences are accepted). Otherwise it returns an error wrapping the new `httphelper.ErrInvalidContentType`.
- `client.Discover` now uses `HttpJSONRequest`; the error is still joined with `oidc.ErrDiscoveryFailed`, so existing `errors.Is(err, oidc.ErrDiscoveryFailed)` checks keep working.
- `HttpRequest` itself is unchanged (it now delegates to a shared internal helper), so token, introspection, userinfo etc. callers are not affected.

# Additional Changes

- Adds `TestDiscover_ContentType` (accepted: `application/json`, with charset, mixed case; rejected: missing, `text/plain`, `text/html`).
- The httptest discovery servers in `pkg/client/rp/relying_party_test.go` now set `Content-Type: application/json`, as a compliant OP would.

Note for reviewers: this makes discovery stricter, so a non-compliant provider that serves its configuration with a wrong content type will now fail discovery. That is what the issue asks for; happy to put it behind an option instead if you'd prefer a softer rollout.
